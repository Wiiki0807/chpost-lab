## 挑戰 A：新增儀表板圖表（適合前端 / 全端）

在 `dashboard.html` 加一張**跨局時效熱區圖**：X 軸為收寄局，Y 軸為投遞局，
顏色深淺代表平均時效天數。

建議做法：

1. 先用 Agent mode 產生後端聚合端點
2. 再用 inline chat 調整前端圖表

參考 prompt：

```text
新增 GET /api/v1/sla/heatmap 端點，回傳收寄局與投遞局兩兩配對的平均時效天數。
照既有三層寫法，補 pytest。
然後在 dashboard.html 加一張 Chart.js 的 matrix 圖呈現這份資料。
```

驗收：圖能顯示、`pytest` 全綠。

## 挑戰 B：新增端點與完整測試（適合後端）

實作 `GET /api/v1/anomalies`：找出投遞量異常的月份與局號。
異常定義自己決定（例如超過該局 12 個月平均的 2 個標準差）。

建議做法：用你在 Lab 3 建立的 `/new-endpoint` prompt file。

參考 prompt：

```text
/new-endpoint

端點：GET /api/v1/anomalies
需求：找出投遞量異常的月份與局號。異常定義為該月件數超過該局 12 個月移動平均的 2 個標準差。
支援 office_code 與 threshold 兩個選填參數，threshold 預設 2.0。
```

驗收：端點可用、測試涵蓋正常路徑與邊界情況、`pytest` 全綠。

## 挑戰 C：補齊文件（適合 PM / QA / 架構師）

這個 repo 沒有 README，API 也沒有文件。把它補完。

建議做法：

```text
#codebase 幫我寫一份 README.md，包含：
- 這個專案在做什麼（三句話以內）
- 架構說明與資料流
- 如何安裝與啟動
- 如何跑測試
- 目前提供的 API 端點清單與用途

用繁體中文，技術名詞保留英文。不要寫你沒在程式碼裡看到的東西。
```

接著再產一份 API 文件：

```text
#codebase 幫我為每個 API 端點寫說明文件，放在 docs/api.md。
每個端點要有：路徑、參數、回傳格式範例、錯誤情況。
回傳格式範例請根據實際的 Pydantic model 產生，不要編造。
```

**注意最後那句「不要編造」。** 這是文件類任務最重要的一句話。

驗收：README 與 API 文件的內容與實際程式碼相符，沒有幻覺內容。

## 觀看版重點：導入建議

### 成功導入的三件事

1. **repo 層的 custom instructions** — 今天就能做
2. **團隊共用的 prompt file 庫** — 一個月內累積
3. **明確的 review 責任歸屬** — 誰按 merge 誰負責

### 治理要看的三個東西

- **content exclusion**：哪些檔案不讓 Copilot 讀
- **授權管理**：誰有、用不用、要不要回收
- **usage metrics**：採用率、接受率。用來找需要協助的團隊，**不是用來考核個人**

### 常見失敗模式

| 失敗模式 | 症狀 | 解法 |
|---|---|---|
| 任務太大 | agent 跑很久、改一堆檔案、越改越亂 | 拆小，每個任務要能一句話說清驗收條件 |
| 沒給 context | 答案很通用、在瞎猜 | `#codebase`、開對的 tab、寫 instructions |
| 盲信 diff | merge 後才發現問題 | diff 一行一行看，這是你的責任 |
| 沒有共用規範 | 每個人產出風格都不一樣 | repo 層 instructions |

### 安全底線

**AI 產出的 code 一樣要走 code review、SAST、依賴掃描。沒有例外。**
